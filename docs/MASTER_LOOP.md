# CRYPTOCHECK AI — MASTER LOOP

### The standing protocol for ANY iterative work on this codebase. Not feature-specific — plug a new mission into Step 1 and the rest applies automatically, every time.

Agent rule (always applied): `.cursor/rules/master-loop.mdc`

---

## Product north star

CryptoCheck AI is **not** building another crypto platform.

CryptoCheck AI is replacing the trader's daily work.

Every feature must move work from the human to the AI.

The final product is not an assistant.

It is an **autonomous financial operating system**.

If a feature still requires the user to search, compare, analyze, or monitor manually, the feature is unfinished.

---

## STEP 0 — AUDIT BEFORE BUILD (always first, no exceptions)

Before writing any code for any new task:

1. Search the codebase for existing engines, components, or logic that already do this or something close to it.
2. State explicitly what already exists and will be reused, versus what's genuinely new.
3. If something looks duplicated, that's a stop signal — reuse or extend, never build a second version of something that already exists.

This step alone has prevented the most expensive mistakes in this project's history: rebuilding the Intelligence Swap from scratch, duplicating Decision logic across surfaces, recomputing what the Decision Engine already computed.

## STEP 1 — MISSION AND SCOPE (fill this in per task)

```
Mission: [what this specific loop is trying to achieve]
Scope (files/directories this loop may touch): [explicit list or boundary]
Layer boundary: [Layer 4 presentation only? Layer 1 engine work? Never touches Decision Engine/Layer 1 unless explicitly stated]
Explicitly out of scope: [what this loop must NOT touch or relitigate]
```

Every loop declares its scope before starting. A loop with no stated boundary tends to expand until someone stops it — the boundary is what makes "keep iterating" safe to authorize.

---

## STEP 2 — THE STANDING SAFETY CARVE-OUT (applies to every loop, unconditionally)

No mission, no north star, and no "reduce friction" instruction ever overrides these, regardless of how the task is framed:

- **Simulate-before-sign** — every transaction is dry-run checked before reaching a wallet signature prompt.
- **Security Scanner critical-flag blocking** with typed override — never weakened for speed or conversion.
- **Real total cost always visible** before any execute action — never collapsed away.
- **The wallet's own signature prompt** stays genuine and unmodified — it was never this app's to alter.
- **Confirmation friction scales up, never down, with unusual position size.**
- **No fabricated data, ever** — no placeholder numbers presented as real, no "LIVE" badge without real provenance, no sample data silently standing in for real history, no demo fallback presented as live. If real data isn't available, the honest state is "not enough data yet" or "unavailable" — never a plausible-looking fake.
- **No claim of guaranteed outcomes** — "no losses," "never wrong," or equivalent language is never acceptable in UI, copy, or marketing generated by any loop.
- **Full autonomy is never the default** for anything that moves real capital. Advise-only is the default; higher autonomy tiers are explicit, user-opted-in, and capped.

Any loop iteration that proposes touching one of these gets flagged and rejected automatically, regardless of how well it serves the loop's stated mission.

---

## STEP 3 — THE ONE-DECISION ARCHITECTURE BOUNDARY (applies to every loop)

No Layer 4 surface (Chart, Coach, Gateway, Swap, Alerts, Discovery, Execution) computes its own opinion, score, or confidence. All of them read the real `Decision` object, produced only by the Decision Engine from Layer 1 engine inputs. This is CI-enforced — any loop that finds itself writing scoring logic inside a Layer 4 component has drifted out of bounds and should stop and re-route through the Decision Engine instead.

---

## STEP 4 — THE BOUNDED ITERATION LOOP

```
Repeat up to N times (default N = 5, state explicitly if different):

  1. Inspect the current state against the Step 1 mission.
  2. Identify SPECIFIC, nameable weaknesses — never a vibe or a bare score.
     ("Execute button is below the 44px touch target minimum" — not "feels small.")
  3. Make ONE focused change addressing one weakness.
  4. Run the objective checks (Step 5). All must pass before continuing.
  5. Log: what changed, why, before/after evidence.
  6. If no further SPECIFIC weakness can be named AND all objective checks pass,
     stop early — don't iterate for the sake of hitting N.

Stop unconditionally at N iterations regardless of subjective feeling.
```

One change per iteration, not a full rewrite each pass — this is what prevents thrashing (undoing iteration 2's decision in iteration 4).

---

## STEP 5 — OBJECTIVE CHECKS (must pass every iteration)

- **Accessibility:** WCAG AA contrast, 44px minimum touch targets, full keyboard navigability of any critical flow touched.
- **No regressions:** existing test suite passes identically; no new console errors.
- **Performance:** no new layout shift, no dropped frames (profiled, not assumed).
- **Data integrity:** every value shown still traces to a real object/engine — the easiest thing to accidentally break during a presentation-focused loop, so check it explicitly every time, not just once.
- **Safety floor:** Step 2's carve-out list, spot-checked intact, every iteration — not just at the end.

---

## STEP 6 — HUMAN CHECKPOINT (never self-certified)

Subjective questions — does this feel trustworthy, premium, institutional, would a professional user trust it — are answered by a human at the end of the loop, using the iteration log and before/after evidence from Step 4. The agent never grades its own subjective quality, with a number or otherwise. Standing three questions, reusable for any surface:

```
1. Does this achieve the Step 1 mission, concretely?
2. Can the answer to "what should I do / what happened / why" be found in the time this surface deserves — no faster than genuine comprehension allows?
3. Any remaining concrete, nameable weakness?
```

If any answer is no — one more scoped round, same protocol, tightened Step 1 scope. If yes — ship.

---

## STEP 7 — HOW TO INVOKE THIS FOR A NEW TASK

A new feature or refinement request going forward should be as short as:

```
MISSION: [one or two sentences]
SCOPE: [files/layer boundary]
OUT OF SCOPE: [what not to touch]
N: [iteration cap, default 5]
Run the Master Loop.
```

Everything else — the safety carve-out, the architecture boundary, the objective checks, the human checkpoint — is already defined here and applies automatically. This is what replaces writing a full bespoke guardrail set for every new ask.

## WHY THIS DOCUMENT EXISTS

Every clause in this loop was earned from something that actually went wrong or nearly went wrong earlier in this build: Discovery silently empty from a calibration bug, LIVE badges on fabricated data, sample data quietly standing in for the real moat feature, an execution pipeline diagram that dropped the approval gate, a "9.7/10" self-score with no ground truth. This document is what keeps those specific mistakes from being repeated under a new feature name.
